# Absorbing a newer CloudCLI UI tag

tether's UI rewrite adopts the *primitive layer* of [CloudCLI UI][upstream]
(`siteboon/claudecodeui`, npm `@cloudcli-ai/cloudcli`) rather than reimplementing
it. The owner's requirement is not "start from v1.37.2" — it is **"and when
upstream ships a good tag later, we can keep absorbing it."** Those are different
requirements, and the second one has to be designed in up front. It cannot be
retrofitted, because by the time you want it the vendored files have already
drifted and there is nothing left to diff against.

This document is the procedure. `scripts/check-vendor-provenance.sh` is the part
of it a machine enforces.

Current baseline: **v1.37.2** / `677b7ba43695d5624d1a981c62f87fa086187991`,
published 2026-08-18, fetched 2026-08-27. The authoritative copy of that pin is
`web/src/vendor/cloudcli.MANIFEST.json`, not this sentence — see "Why the pin is
not written down here" below.

[upstream]: https://github.com/siteboon/claudecodeui

## The three conventions this rests on

### 1. Provenance is per-file, not per-repo

Every vendored file opens with a machine-readable header naming the upstream
path, tag, SHA and fetch date:

```js
/* @tether-vendored - DO NOT EDIT THIS FILE.
 * upstream-repo: https://github.com/siteboon/claudecodeui
 * upstream-path: postcss.config.js
 * upstream-tag: v1.37.2
 * upstream-sha: 677b7ba43695d5624d1a981c62f87fa086187991
 * fetched: 2026-08-27
 * status: pristine
 * ...
 * @tether-vendored-end */
```

A single line in a README saying "based on v1.37.2" would be cheaper and would
be wrong within two absorptions. It is an *applied-changes list*: a summary
maintained by hand, in one place, describing many files, with nothing reading it.
Those rot silently and without exception — and a partial absorption (some files
moved to a new tag, some not) makes a single repo-level version number not merely
stale but unrepresentable.

The header is prose *and* data: it is what a reader hits first when they open the
file with intent to edit it, and it is what the checker parses.

Two properties of that block are enforced rather than assumed, and both are worth
knowing before you hand-edit one:

- **It must be a single self-contained block comment.** Line 1 is exactly
  `/* @tether-vendored - DO NOT EDIT THIS FILE.`, the last line is exactly
  ` * @tether-vendored-end */`, every line between opens ` * `, and no line
  before the terminator contains `*/`. The region above the terminator is
  *trusted* — the content hash starts below it — so it has to be provably inert.
  The first version of this checker parsed six fields out of that region and
  examined nothing else, and a header of the form `... */ <live code> /* ...`
  passed both `check` and `verify-upstream`, the latter reporting the file as
  "byte-identical to the upstream blobs they name" while it ran code upstream
  never shipped.
- **Every byte of it is hashed**, as `header_sha256`, alongside `body_sha256`
  for the bytes below. Shape alone would still leave the prose and the `license`
  lines rewritable in silence. With both, the file has no unexamined region at
  all, and no header edit can happen without a manifest edit landing in the same
  diff.

### 2. Vendored files are never edited in place

This is the load-bearing rule. The moment a vendored file is edited,

```
git diff <pinned-sha>..<newer-sha> -- <upstream-path>
```

stops applying cleanly to it, and the absorption requirement is void for that
file — permanently, because there is no way back to a known-good base.

So upstream's files stay pristine **even where they are wrong for us**. Local
differences are expressed by wrapping, extending or composing, in a separate
directory:

| directory | contents | may be edited |
|---|---|---|
| `web/src/vendor/cloudcli/` | upstream's bytes, unmodified | **no** |
| `web/src/ui/` | tether's wrappers around them | yes |

If a file genuinely cannot be used unmodified, it leaves the absorption chain
explicitly rather than quietly — step 6.

### 3. Provenance is machine-verifiable

`web/src/vendor/cloudcli.MANIFEST.json` maps each vendored path to its upstream
path, tag, SHA and a content hash. `scripts/check-vendor-provenance.sh check`
recomputes the hashes from the files and compares. It runs in CI on every PR,
whatever branch the PR targets, and `make test` runs it too.

**The checker deliberately does not iterate the manifest to decide what to
check.** `web/` has already shipped a gate with that defect: a test named
"exposes exactly the 8 ErrorCode constants" that builds its expectation from the
same eight names it then asserts, so the module's actual ten exports went
unnoticed and an eleventh would have too. A provenance check written as "for each
manifest entry, verify that entry" has the identical blind spot — a vendored file
nobody added to the manifest is a file the loop never visits, and the gate stays
green.

So the file set comes from the filesystem — `find` over the vendor root, unioned
with `git ls-files` so that a file staged and then deleted from the worktree is
still seen — and the manifest and that set must agree **in both directions**. The
rule, stated generally: *a gate's assertion must be derived from the object under
test, not from a copy of it.*

`find` specifically, and not `git ls-files --others --exclude-standard`, which
was the first version of that line. The `--exclude-standard` form honours
`.gitignore`, which silently turns `.gitignore` into an exclusion list for this
gate — and tether's has un-anchored entries (`.env`, `*.out`, `.DS_Store`).
Measured on that version: `echo SECRET=1 > web/src/vendor/cloudcli/.env` and the
check still reported OK. There is now no exclusion list at all: every path under
the vendor root must be declared, full stop.

There is a second thing the checker cannot do by comparing state, and a separate
mode for it — see step 4.

## The procedure

Absorption is triggered by a human deciding a tag is worth having. There is no
automated tag-following on purpose: upstream ships fast (seven tags between
v1.35.1 and v1.37.2), most of it is in areas we do not vendor, and a bot opening
a PR per tag would train everyone to ignore these PRs.

### Step 1 — fetch the candidate tag and write down its SHA

**Clone in full, not `--depth 1`.** A shallow clone carries one commit, and both
of the steps that touch the clone need more than one:

- step 2 diffs *from* each entry's pin *to* the candidate — two endpoints per
  entry, and the pins are not all the same commit;
- step 5 (`verify-upstream`) reads every entry's blob at that entry's own `sha`,
  so it needs every pin the manifest mentions, not just the newest. The script
  says so itself when a lookup misses.

Step 6 touches no clone at all.

```bash
git clone https://github.com/siteboon/claudecodeui /tmp/ccui   # full
git -C /tmp/ccui fetch --tags
git -C /tmp/ccui rev-parse "<new-tag>^{commit}"
```

A `--depth 1` clone is fine only for a first look at a tag, and only while the
manifest sits entirely on one pin.

### Step 2 — diff **each entry from its own pin** to the candidate

```bash
cd /path/to/tether
M=web/src/vendor/cloudcli.MANIFEST.json
NEW=<new-sha>
jq -r '(.vendored + .verbatim)[] | [.sha, .upstream_path] | @tsv' $M | sort -u |
while IFS=$'\t' read -r pinned up_path; do
  echo "=== $up_path   ${pinned:0:7}..${NEW:0:7}"
  git -C /tmp/ccui diff "$pinned".."$NEW" -- "$up_path"
done
```

**Per entry, from that entry's own `sha` — not one base for the whole tree.** The
tempting one-liner is `PINNED=$(jq -r '.pins[.current_baseline]' $M)` followed by
a single diff over all paths, and it is wrong in exactly the situation this
document exists for. Entries are allowed to sit at different tags: a partial
absorption, where some files moved and some were left alone, is a legitimate and
expected state, and the checker validates each entry against its own `(tag, sha)`
rather than forcing them all onto the baseline. So for any entry not currently at
`current_baseline`, a baseline-based diff prints hunks measured from a commit that
file was never at. Apply those and you get a file matching neither tag — and
because `rehash` then records the hash of whatever you produced, `check` goes
green over it. The failure is silent, and it is reached by following the
procedure, which is the worst place to keep a trap.

The path restriction is the other half of the point. Upstream's full diff between
two tags is mostly backend, i18n and feature components we do not carry;
reviewing that is how absorption becomes a job nobody does. Deriving the paths
from the manifest rather than typing them keeps the reviewed set equal to the
carried set.

An empty diff means there is nothing to absorb for the files we hold, even if the
tag is full of other changes. That is a normal and common outcome.

### Step 3 — review each hunk, and **record the rejections**

For every changed file, decide: take it, or don't.

Rejections go into `rejected_upstream_changes` in the manifest:

```json
{
  "tag": "v1.38.0",
  "upstream_path": "src/index.css",
  "reason": "Adds `@import url(https://fonts.googleapis.com/...)`. tether's SPA is served from the binary and must render with no third-party network fetch at all (see K.8.1).",
  "reviewed_on": "2026-09-14"
}
```

All four fields are required and the checker enforces that, `reviewed_on`
included: a rejection with no date cannot be aged out, and "we looked at this
once" is worth much less at the next absorption than "we looked at this at
v1.38.0, on 2026-09-14".

This is the step most likely to be skipped and the most expensive to skip. An
unrecorded rejection is re-litigated at every future absorption, by someone who
does not know it was already decided — so the cost of skipping it is not "we
forget", it is "every subsequent absorption gets more expensive", which is the
failure mode that ends the practice.

Note what a rejection is *not*: it is not an edit. Declining an upstream hunk
means the vendored file stays at its old pin, with its old `tag`/`sha`, and the
rejection is the record of why. It never means taking the tag and then removing
the part we did not like — that is an in-place edit, and step 4's diff gate will
say so.

### Step 4 — apply, then update the manifest

Apply the accepted hunks **to the bytes below the header** and leave the header
block in place. Then update, by hand, in the manifest and in each touched file's
header: `tag`, `sha`, `fetched`. `upstream_path` moves too if upstream renamed
the file — it is the path the next diff will be taken against, so a rename that
is not recorded here makes step 2 look at nothing. Add the new tag to `.pins`
(never overwrite an existing one — see below) and move `.current_baseline`. Then:

```bash
bash scripts/check-vendor-provenance.sh rehash
```

`rehash` recomputes the content hashes and `header_sha256` — nothing else. It
never touches `tag`, `sha`, `upstream_path` or `status`, because those are claims
a human is making and a calculator must not be able to make them true. It exits
non-zero whenever it changes anything, so `rehash && check` cannot report a clean
pass, and it refuses outright to rehash a file whose header region is not a
self-contained block comment.

Be precise about the limit of that, because it is easy to over-trust: the
manifest is already written by the time `rehash` exits, so `rehash ; check` —
semicolon, or simply two commands typed in turn — **does** go green on an
in-place edit. `check` compares the tree against the manifest, and after the
rehash those two agree perfectly; there is nothing inconsistent left for it to
find. An earlier version of this document said "nothing offline can close that"
and asked reviewers to paste `verify-upstream` output into any PR touching a
hash. That was wrong on the first count and, on the second, was a request
addressed to people on the one path where this whole arrangement fails silently.

What closes it offline is reading the **change** instead of the state:

```bash
bash scripts/check-vendor-provenance.sh check-diff @origin/main   # or: make check-vendor-diff BASE=@origin/main
```

Upstream cannot alter its own bytes at a fixed sha. So

> a `*_sha256` that moves while that entry's `tag`, `sha` and `status` all stay
> put **is** an in-place edit that was rehashed

is not a heuristic, it is the definition, and it is decidable from two manifests
with no network at all. `check-diff` asserts it, plus two corollaries of the same
argument: `.pins` is append-only (a pin records what upstream published at a tag
— that is history, and history is appended to, not corrected), and a file that
newly goes `detached` must name the sha it was actually pinned at as its
`detached_from_sha`.

Because it is offline and deterministic, the objection that keeps
`verify-upstream` out of CI does not apply to it: **`check-diff` runs on every
PR**, against the PR base. The rule that used to be a sentence here is now a
check, which is the difference between a convention and a gate.

A legitimate absorption passes it by construction — you moved `tag` and `sha`, so
the hash is allowed to move with them. If it goes red, the honest options are to
absorb a tag properly or to detach the file deliberately (step 6). Editing in
place and rehashing is the one thing it will not let through quietly.

### Step 5 — re-run all three checks

```bash
bash scripts/check-vendor-provenance.sh check
bash scripts/check-vendor-provenance.sh check-diff @origin/main
bash scripts/check-vendor-provenance.sh verify-upstream /tmp/ccui
```

or, equivalently, `make check-vendor`, `make check-vendor-diff BASE=@origin/main`
and `make verify-vendor-upstream CLONE=/tmp/ccui`.

The three assert different things, and none of them subsumes another:

| | compares | catches | in CI |
|---|---|---|---|
| `check` | tree ↔ manifest | drift, undeclared files, header tampering | every PR |
| `check-diff` | manifest ↔ manifest at the base | a hash that moved with no pin behind it | every PR |
| `verify-upstream` | manifest ↔ upstream's blobs | a recorded hash that upstream never published | no — by hand |

**All three are required during an absorption, and this is not belt-and-braces.**
Measured on this repo: edit a vendored file, run `rehash`, and `check` passes
(hash matches the freshly written record, headers agree, coverage agrees), while
`verify-upstream` reports

```
FAIL: postcss.config.js: manifest hash is not what upstream published at 677b7ba...
        manifest: ec7ed55d613b3ac1...
        upstream: 010e8774c76996e2...
```

and `check-diff` reports the same event offline, from the manifest diff alone:

```
FAIL: [hash-moved-alone] postcss.config.js
      content hash moved 010e8774c769 -> ec7ed55d613b while tag (v1.37.2), sha and
      status all stayed put. ...
```

`verify-upstream` remains the only one of the three that can catch a *wrong
record*: a hash and a sha written down together that never went together
upstream. `check-diff` cannot see it — a hash that moves *with* its pin is
exactly what a real absorption looks like — and nothing offline can, because
nothing offline knows what upstream published. It is not the per-PR gate because
it reaches github.com, and a gate that goes red when a third party has a bad
afternoon is one people learn to rerun past.

So be exact about what is enforced and what is not. Editing a vendored file in
place is now gated by machine, in CI, on every PR: `check` if you forget to
rehash, `check-diff` if you remember to. Recording a *false pin* is not gated,
and cannot be offline — that one is still a human step, and the honest statement
of it is that a reviewer who wants proof of the pin runs `verify-upstream`
themselves against a clone. It is one command and needs nothing from the author.

### Step 6 — if a file must fork, detach it deliberately

If a vendored file cannot be used unmodified and wrapping genuinely will not do,
it leaves the absorption chain — but on the record. Set `status` to `detached` in
both the manifest and the file's header, and add:

```json
"detached_from_sha": "677b7ba43695d5624d1a981c62f87fa086187991",
"detached_reason": "why wrapping was not sufficient"
```

The checker requires both fields for a detached entry, and keeps verifying the
file's hash so a detached file cannot drift further without notice. What it no
longer claims is equality with upstream.

Prefer wrapping. Every detached file is a file whose upstream improvements now
have to be ported by hand, forever.

## Adding or removing a vendored file

Absorption moves existing entries. This is the other axis: changing *which* files
we carry. It is not part of an absorption and should not be mixed into one — a PR
that both moves the baseline and changes the carried set is a PR where nobody can
tell which diff is upstream's.

### Adding one

1. Decide it whole. **Vendor the entire file or none of it.** A partially copied
   file cannot be diffed against a future tag, which is the only reason any of
   this exists; there is no such thing as vendoring the interesting half.
2. Copy the bytes out of the clone at the pin you want, and prepend the header —
   thirteen lines, in the shape §1 describes, `status: pristine`. Keep the local
   path identical to the upstream path; the tree under `vendor_root/` mirrors
   upstream's, so nothing has to remember a mapping.
   ```bash
   V=web/src/vendor/cloudcli
   P=src/index.css            # upstream path == local path
   mkdir -p "$V/$(dirname $P)"
   { cat header.txt; git -C /tmp/ccui show "<sha>:$P"; } > "$V/$P"
   chmod 0644 "$V/$P"
   ```
3. Add the manifest entry: `path`, `upstream_path`, `tag`, `sha`, `fetched`,
   `status`, `layer`. Leave `body_sha256` and `header_sha256` out and let
   `rehash` compute them — hand-typed hashes are how a hash and its file stop
   being related.
4. `rehash`, then `check`, then `verify-upstream <clone>`. The last one is the
   step that proves the bytes really are upstream's; run it before pushing, not
   after. `check-diff` will report the entry as new, which it is — a new hash is
   not a moved hash.

File mode is normalised to `0644`. Upstream ships some of these as `0755`; mode
is not content, is not part of any diff we intend to apply, and is not part of
the pristine claim. Only the bytes are.

`LICENSE`, `NOTICE` and `COPYING` are the only paths that may be declared
`verbatim` (no header, whole file hashed), and only at the root of the vendor
tree. Inserting text into a licence document is not a thing to do; `verbatim` is
not a way to opt a source file out of carrying a header.

That pairing has a consequence worth knowing before you hit it: the header is a
`/* … */` block comment on line 1, so a file type that cannot carry one there —
JSON, or anything needing a shebang first — has no home under this scheme yet.
Vendoring one means extending the checker (a per-type comment syntax, or a
sidecar hash for headerless entries), not widening `verbatim`. Nothing upstream
that we want is in that shape today.

### Removing one

Delete the file and its manifest entry in the same commit. `check` reddens on
either half alone — a declared file that is gone, or a file that is present and
undeclared — so there is no way to do half of it quietly. If the file is being
replaced by tether's own implementation, say so in the commit message; the
absence of a `rejected_upstream_changes` entry will otherwise read as an
oversight at the next absorption.

Do not remove its tag from `.pins` while any other entry still names it, and
prefer not to remove pins at all: `check-diff` treats `.pins` as append-only, and
a pin costs one line.

## Why the pin is not written down here

The tag and SHA live in `web/src/vendor/cloudcli.MANIFEST.json` and in each
file's header, both of which are checked against the files by CI. The baseline
named at the top of this document is a convenience copy with nothing enforcing
it, and it may be stale — the manifest is authoritative. Cross-file and
cross-repo copies of a fact decay independently of the fact; that is why the
enforced record is the one in the tree with the code.

This document lives in tether rather than in `tether-doc` for the same reason: it
is executed by someone standing in this repo running that script, and a procedure
kept in another repository drifts out of sight of the thing it governs.

The per-file provenance header discharges §7(c) at the finest available
granularity, and the `status: pristine` / `status: detached` field is exactly the
"is this modified" marking §7(c) asks for. The attribution block in `README.md`
is aimed at §7(b).
